The [odio application](https://pwa.odio.love) is a web app that lets you manage all your odio nodes from one place. Install it from your browser on your phone or desktop.

## How it works

The application loads each node's [embedded web UI](/control/embedded-ui/) in an iframe. You get the full interface of each node, playback, audio routing, Bluetooth, services, power, all accessible from a single app.

## Installation

1. Open [pwa.odio.love](https://pwa.odio.love) in your browser.
2. Tap "Install" or "Add to Home Screen" when prompted.
3. Add your nodes by hostname or IP, or [scan your network](#network-scan) for them.

**Browser support.** On mobile, installation works on Chrome, Edge, Safari, and Firefox. On some browsers like DuckDuckGo, the option is in the three-dot menu. On desktop, Chrome and Edge can install the app; Firefox and Safari desktop hit browser-level restrictions on [LAN access](#lan-access).

## Adding nodes

A web app cannot perform mDNS/Zeroconf discovery, browsers don't have access to UDP multicast. Add your nodes by hostname or IP, or [scan the network](#network-scan) for them.

On first launch, click **+ Add Instance** and enter the host/IP, port (default 8018), and an optional label for your node. Add as many as you have, each card shows the node name, architecture, odio-api version, and connection status. Click **Connect** to open the node's interface.

### Network scan

Since [v0.7.0](https://github.com/b0bbywan/odio-pwa/releases/tag/v0.7.0), **Scan network** probes every host of a target and lists the nodes that answer, each with an **Add** button, plus **Add all**. The target is an IP or hostname, or a network with its mask (`192.168.1.0/24` or `192.168.1.0/255.255.255.0`), up to a /22.

A browser can't read its own IP, so with the target left empty the app works out where to look:

1. If a node of your list is online and was added by IP, its /24 is scanned straight away.
2. Otherwise around forty networks are checked: the /24 of the nodes of your list that are offline, then the defaults of common routers, ISP boxes and hotspots.
3. If none of them is connected, the rest of `192.168.0.0/16` is swept.

Limits:

- Only directly connected networks are found, one behind another router has to be entered by hand.
- `10.0.0.0/8` and `172.16.0.0/12` are too large to sweep, only a few known defaults are checked there.
- Only nodes that allow the PWA's origin are listed. Hosts that answer on the port without allowing it are counted apart, next to the origin to add to their [`api.cors.origins`](/api/configuration/#cors).

How a connected network is told from one that isn't is described in the [odio-pwa README](https://github.com/b0bbywan/odio-pwa#network-scan).

## Node cards

Since [v0.6.0](https://github.com/b0bbywan/odio-pwa/releases/tag/v0.6.0), the card of an online node shows its active [MPRIS](/api/mpris/) player: cover, title, artist and album, a progress bar, and previous / play-pause / next. Click the cover to zoom it. When several players are active, tabs switch between them. Since [v0.7.0](https://github.com/b0bbywan/odio-pwa/releases/tag/v0.7.0), only the commands the player supports are shown, and the progress bar only for players that can seek.

A power icon in the card header powers the node off, after a confirmation, when its [power backend](/api/power/) allows it.

Nodes that are playing are listed first, then paused ones, then idle ones, unreachable ones last. The order is settled when the list is shown or on **Refresh all**, so a card never moves while you are using the list.

## Open a node by URL

Since [v0.5.0](https://github.com/b0bbywan/odio-pwa/releases/tag/v0.5.0), the active instance lives in the URL, so any node can be opened directly:

```
https://pwa.odio.love/#/i/<host>[/<port>][?label=<name>]
```

Port and label are optional. First-time visits stay transient and the app prompts to save on exit. Hash routing also means refresh and the back/forward buttons behave like any other web app.

odio also print the matching link in the SSH MOTD, so SSH'ing to a node gives you a one-click path to its UI in the PWA.

## In-app diagnostics

The application surfaces the situations described below directly in the UI so you don't have to dig through devtools to know what's wrong.

### Unsupported browser banner

When the PWA detects Firefox or Safari desktop on an HTTPS context (the combinations that cannot reach LAN nodes at all), it shows a persistent banner pointing back at this guide and disables the **+ Add Instance** and **Scan network** buttons. There is nothing useful those browsers can do without switching browser or [self-hosting over HTTP](#multiple-nodes-no-install-self-host-over-http).

### Per-card status messages

When a probe fails for an existing node, the card re-probes with `mode: 'no-cors'` to tell three failure modes apart:

| Card message | Color | What it means |
| --- | --- | --- |
| *Server unreachable* | red | The server is down, or the request was blocked at the network layer. |
| *Server reachable: missing CORS headers* | amber | The request round-tripped but the response lacks `Access-Control-Allow-Origin`. Add the PWA's origin to [`api.cors.origins`](/api/configuration/#cors). |
| *Browser blocked (mixed content)* | amber | Both probes failed on Firefox or Safari desktop over HTTPS, for a node that isn't on loopback: the browser blocks the request as mixed content. Use Chrome 142+ with LNA granted, or self-host over HTTP. |

Since [v0.5.5](https://github.com/b0bbywan/odio-pwa/releases/tag/v0.5.5), *Browser blocked* is only reported where the browser does block: on Chrome, Edge and mobile browsers, a node that doesn't answer is *Server unreachable*.

The amber messages embed a link to the relevant docs section so you can jump straight from the card.

### Connection-status screens

Since [v0.5.0](https://github.com/b0bbywan/odio-pwa/releases/tag/v0.5.0), clicking **Connect** on a node that doesn't respond shows a dedicated *Connecting*, *Server unreachable*, or *Browser blocked* view instead of the native broken-iframe error. Deep links to a host you've never reached land on the same screen rather than the *Server is shutting down* overlay.

## Browser limits and alternatives

### LAN access

<Aside type="caution">
pwa.odio.love is served over HTTPS while odio nodes on your LAN typically run over HTTP. This is mixed content, and browsers handle it differently:

- **Chrome 142+** prompts for Local Network Access and works once granted.
- **Safari** blocks mixed content with no exemption.
- **Firefox** only exempts `localhost`, so nodes on your LAN are blocked.
</Aside>

pwa.odio.love is the easiest path, but it's not the only one. If your browser blocks mixed content, doesn't support PWA install, or you only have one node, these alternatives may fit better.

### Single node: bookmark the embedded UI

If you only have one odio node, the PWA isn't really needed. Bookmark the node's [embedded web UI](/control/embedded-ui/) directly, it's the simplest option, especially on a browser that doesn't allow PWA install.

### Multiple nodes, no install: self-host over HTTP

If you have several nodes and don't need the installable-app experience, self-host the PWA on your LAN over plain HTTP. No mixed-content restriction, no CORS setup, just bookmark the address and access it from any device on your network. See [Self-hosting](#self-hosting) below.

### Multiple nodes with install: self-host over HTTPS

To keep PWA install, self-host the PWA over HTTPS on a local address, for example with [Traefik](https://traefik.io/) and Let's Encrypt. The mixed-content situation is unchanged since the HTTPS PWA still calls HTTP nodes, so this setup still requires a Chromium-based browser (Chrome 142+ with LNA granted, or Edge). Add your self-hosted origin to [`api.cors.origins`](/api/configuration/#cors) in each node's config so the API accepts requests from your PWA, see [CORS on each node](#cors-on-each-node) below.

## Self-hosting

Self-hosting has always been possible by cloning and building the repo yourself. [v0.3.4](https://github.com/b0bbywan/odio-pwa/releases/tag/v0.3.4) makes it easier with an official Docker image and a ready-to-deploy static zip.

<Aside>
Thanks to [@pbattino](https://github.com/pbattino) ([odios#47](https://github.com/b0bbywan/odios/issues/47)) for the nudge to package and document self-hosting properly.
</Aside>

- **Docker** (multi-arch, amd64 + arm64):

  ```bash
  docker run -d -p 8080:80 --restart unless-stopped \
    --name odio-pwa ghcr.io/b0bbywan/odio-pwa:latest
  ```

  The image is based on `nginx:alpine` with SPA fallback and PWA-aware cache headers already configured.

- **Static zip** — download `odio-pwa-<version>.zip` from the [releases page](https://github.com/b0bbywan/odio-pwa/releases) and serve the extracted files from any web server. Make sure unrecognized paths fall back to `/index.html`, and set `Cache-Control: no-cache` on `/index.html`, `/sw.js`, and `/registerSW.js`.

### CORS on each node

If you serve the PWA over HTTPS, the API on each node must accept your origin. Add it to [`api.cors.origins`](/api/configuration/#cors) in every node's config. The list **replaces** the defaults, so include the hosted addresses too if you want to keep them reachable:

```yaml
api:
  cors:
    origins:
      - https://pwa.odio.love
      - https://odio-pwa.vercel.app
      - https://odio.yourdomain.com   # your self-hosted origin
```

HTTP self-hosting on the LAN doesn't require this, see [Browser limits and alternatives](#browser-limits-and-alternatives) above.

### Updates

An arrow indicator appears next to the app version when a newer GitHub release is available, click it to open the release notes. To include prereleases (for testing RCs), run in the browser devtools console:

```js
localStorage.setItem('odio-include-prereleases', 'true')
```
