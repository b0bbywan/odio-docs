Each section links the workflow files, so you can jump straight to the part you care about.

## Shared CI plumbing

[odio-ci](https://github.com/b0bbywan/odio-ci) holds what the packaging repos would otherwise repeat. The build itself stays in each repo, because the builds genuinely differ.

| Piece | What it does | Used by |
|---|---|---|
| [`release.yml`](https://github.com/b0bbywan/odio-ci/blob/main/.github/workflows/release.yml) | Collects the per-arch artifacts, fails when no `.deb` came out, derives the prerelease flag from the tag, creates the Release and dispatches odio-apt-repo | odioctl, odio-framebuffer-ui, odio-mympd, odio-qbz, odio-upmpdcli, gstreamer1.0-openaptx |
| [`watch-upstream.yml`](https://github.com/b0bbywan/odio-ci/blob/main/.github/workflows/watch-upstream.yml) | Resolves an upstream project's latest GitHub release and pushes a matching tag when it's new. The cron stays in the caller, a reusable workflow has no trigger of its own | odio-mympd, odio-qbz |
| [`resolve-version`](https://github.com/b0bbywan/odio-ci/tree/main/actions/resolve-version) | Turns the trigger into an upstream tag and a Debian version | odio-mympd |
| [`check-binary`](https://github.com/b0bbywan/odio-ci/tree/main/actions/check-binary) | Gates provable from the ELF alone, no board or QEMU needed: machine matches the package arch, ARM baseline is what it claims (an ARMv7 build `SIGILL`s on a Pi 1 or Zero), glibc floor no higher than Raspberry Pi OS, `NEEDED` printed to cross-check `Depends` | odio-framebuffer-ui, odio-mympd, gstreamer1.0-openaptx |

A release candidate tag like `v2.0.2-rc1` builds upstream `v2.0.2` and versions the package `2.0.2~rc1`, with a tilde: Debian sorts `~` below the final release, while a dash would sort above it and apt would never upgrade off the RC.

Callers pin an exact `vX.Y.Z`. GitHub's immutable releases freeze a tag once released, so there is no floating `v1` to move forward; Dependabot bumps the pins instead.

## The component release chain

Eleven repos feed `.deb` into [apt.odio.love](https://apt.odio.love):

| Repo | Build | Arches |
|---|---|---|
| [go-odio-api](https://github.com/b0bbywan/go-odio-api) | Go cross-compile, packed with [nfpm](https://nfpm.goreleaser.com/), plus `.rpm` and a multi-arch GHCR image | amd64, arm64, armhf, armv7hf |
| [odioctl](https://github.com/b0bbywan/odioctl) | Go, smoke-tested in a container, plus bare binaries | amd64, arm64, armhf |
| [go-mpd-discplayer](https://github.com/b0bbywan/go-mpd-discplayer) | Go with cgo, ARM builds inside Raspberry Pi OS images under QEMU | amd64, arm64, armhf, armv7hf |
| [mpd2mpris](https://github.com/b0bbywan/mpd2mpris), [snapclientmpris](https://github.com/b0bbywan/snapclientmpris) | Pure Python, built once in a `debian:trixie` container | all |
| [odio-framebuffer-ui](https://github.com/b0bbywan/odio-framebuffer-ui) | `dpkg-buildpackage` in per-arch `debian:trixie` builder images, `lintian` | amd64, arm64 |
| [spotifyd](https://github.com/b0bbywan/spotifyd) | Rust fork, in a builder image | amd64, arm64, armhf |
| [odio-mympd](https://github.com/b0bbywan/odio-mympd) | Upstream myMPD in per-arch builder images rebuilt [monthly](https://github.com/b0bbywan/odio-mympd/blob/main/.github/workflows/build-images.yml) | amd64, arm64, armhf |
| [odio-qbz](https://github.com/b0bbywan/odio-qbz) | Upstream qbz tag plus the patches in `patches/`, `qbzd` daemon only, ELF gates in the builder | amd64, arm64, armhf |
| [odio-upmpdcli](https://github.com/b0bbywan/odio-upmpdcli) | No build: upstream Debian packages republished unchanged | amd64, arm64, armhf, all |
| [gstreamer1.0-openaptx](https://github.com/b0bbywan/gstreamer1.0-openaptx) | Debian's `gst-plugins-bad1.0` source, only `ext/openaptx/` compiled | amd64, arm64, armhf |

The flow is the same for all of them:

1. A `v*` tag is pushed, by hand or by an upstream watcher.
2. `build.yml` produces the `.deb`.
3. A GitHub Release is created with every `.deb` attached.
4. A `repository_dispatch` of type `release-published`, signed with `APT_REPO_TOKEN`, tells [odio-apt-repo](https://github.com/b0bbywan/odio-apt-repo) to rebuild.

Every `armhf` package targets ARMv6, so it runs on a Pi 1 or Zero; go-odio-api and go-mpd-discplayer add an ARMv7 build as `armv7hf`. Where armhf is compiled natively rather than cross-compiled, it runs under QEMU, since GitHub's ARM runners can't execute 32-bit ARM code. For odio-qbz that takes hours where amd64 and arm64 take minutes, hence a longer timeout and a build cache.

### Tracking upstream

Four repos package someone else's project. They vendor no source, only CI.

| Repo | Upstream | New version detected by |
|---|---|---|
| odio-mympd | [jcorporation/myMPD](https://github.com/jcorporation/myMPD) releases | odio-ci's watcher, daily at 06:17 UTC |
| odio-qbz | [vicrodh/qbz](https://github.com/vicrodh/qbz) releases | odio-ci's watcher, daily at 06:23 UTC |
| odio-upmpdcli | The upstream APT repositories on [lesbonscomptes.com](https://www.lesbonscomptes.com/upmpdcli/) | Its [own watcher](https://github.com/b0bbywan/odio-upmpdcli/blob/main/.github/workflows/watch-upstream.yml), daily at 06:41 UTC, comparing the packages with the latest release |
| gstreamer1.0-openaptx | `gst-plugins-bad1.0` in Debian trixie | Tagged by hand, following the GStreamer version trixie ships |

odio-ci's watcher pushes its tag with [`RELEASE_PAT`](#secrets-and-trust). odio-upmpdcli does without: it pushes the tag with `GITHUB_TOKEN`, then starts `build.yml` on it with a `workflow_dispatch`, which that token is allowed to trigger.

The `b0bbywan/spotifyd` fork carries CI-only commits, but the source lives in the repo, so it keeps a build workflow of its own rather than this shape.

### The apt repository rebuild

[odio-apt-repo](https://github.com/b0bbywan/odio-apt-repo/blob/master/.github/workflows/update-repo.yml) receives the dispatch and rebuilds from scratch:

- `gh release list` resolves the latest stable and latest prerelease of every repo above. A manual `workflow_dispatch` accepts a version override per repo.
- Only the `.deb` a previous run didn't fetch are downloaded: `debs/` is cached on the resolved versions, so a rebuild that finds nothing new downloads nothing and the download counters stay honest.
- [`reprepro`](https://salsa.debian.org/debian/reprepro) assembles two suites, `stable` and `testing`, across `amd64`, `arm64`, `armhf`, and `armv7hf`.
- The tree is GPG-signed, written with a `CNAME` for `apt.odio.love`, and deployed to [GitHub Pages](https://pages.github.com/).

A cron reruns it every Monday and Thursday at 04:00 UTC, so a missed dispatch never leaves the repo stale for long, and the `.deb` cache stays inside the seven days after which GitHub evicts it.

## odios releases

[odios](https://github.com/b0bbywan/odios) ships the installer, not `.deb` packages. On a CalVer tag like `2026.4.1`, [`release.yml`](https://github.com/b0bbywan/odios/blob/main/.github/workflows/release.yml) runs:

| Stage | What it does |
|---|---|
| Gate | Reuses [`checks.yml`](https://github.com/b0bbywan/odios/blob/main/.github/workflows/checks.yml), so a red lint or test never produces a release |
| Package | Vendors `ansible-core` as pure Python and packs `odio-<version>.tar.gz` with `install.sh` and `manifest.json` |
| Playbook test | Full run on `ubuntu-latest` with an idempotence rerun, then a single pass on native ARM64 and on ARM/v7 + ARM/v6 under [QEMU](https://www.qemu.org/) (ARM/v6 marked experimental) |
| Install test | `test.sh` in `install` and `install-root` modes against the just-published pre-release, through the real `curl` one-liner |
| Upgrade test | A matrix over baselines of every supported `state.json` generation, detailed below |
| Images | Raspberry Pi images (`odio-*.img.xz`) for armhf and arm64 |
| Imager manifest | A combined `odio.rpi-imager-manifest` for [Raspberry Pi Imager](https://www.raspberrypi.com/software/). Pre-releases also get one per arch, so a PR can be tested in Imager as soon as one arch is built |

The upgrade matrix enters through every path a node can take: the last published `odio_upgrade.py` over `curl` (the migration off a pre-[odioctl](/operations/settings/) baseline), `odioctl upgrade apply`, `odio-upgrade.service` via `systemctl --user` (which exercises the sudoers switch to the `odioctl` group), and a `--progress` run asserting the `ODIO_PROGRESS` events. Two more entries cover an upgrade triggered by a user other than the target user, and baselines installed without the MPD stack. The baselines live at `ghcr.io/b0bbywan/odios/test-baseline:<tag>-<arch>`: arm64 ones are converted from the published SD images by [`img-to-docker.sh`](https://github.com/b0bbywan/odios/blob/main/scripts/img-to-docker.sh), amd64 ones are layered onto `Dockerfile.test` by [`build-baseline-amd64.sh`](https://github.com/b0bbywan/odios/blob/main/scripts/build-baseline-amd64.sh) so the systemctl path runs under real systemd-logind without QEMU.

Pull requests run the same matrix against a `pr-<N>` pre-release, so the install path you'd take is tested before merge, not only before release.

Everything lands on a single [GitHub Release](https://github.com/b0bbywan/odios/releases). `odio.love/install`, `/manifest.json`, and `/odio.rpi-imager-manifest` are 307 redirects from the [odio.love](https://github.com/b0bbywan/odio.love) site to `releases/latest/download/<asset>`, so `curl -fsSL https://odio.love/install | bash` never changes. To pin a version, call the GitHub URL with the tag, as shown in [Upgrade](/operations/upgrade/).

## PWA, Home Assistant, and PyPI

- [odio-pwa](https://github.com/b0bbywan/odio-pwa)'s [`release.yml`](https://github.com/b0bbywan/odio-pwa/blob/main/.github/workflows/release.yml) zips the built `dist/` as `odio-pwa-<version>.zip` and builds the Docker image for amd64 and arm64 on native runners, merged into one multi-arch tag on `ghcr.io/b0bbywan/odio-pwa`. Only stable releases move `:latest`.
- [odio-ha](https://github.com/b0bbywan/odio-ha)'s [release workflow](https://github.com/b0bbywan/odio-ha/blob/master/.github/workflows/release.yml) waits for CI to pass on the tag, via `workflow_run`, before creating the release. Prereleases are detected from the tag suffix (`-alpha`, `-beta`, `-rc`).
- [mpd2mpris](https://pypi.org/project/mpd2mpris/), [snapclientmpris](https://pypi.org/project/snapclientmpris/), and [pyodio](https://pypi.org/project/pyodio/) publish their sdist and wheel through PyPI [trusted publishing](https://docs.pypi.org/trusted-publishers/). Every tag goes to [TestPyPI](https://test.pypi.org/), only final releases continue to PyPI.

## Secrets and trust

| Secret | Held by | Used for |
|---|---|---|
| `APT_REPO_TOKEN` | The repos publishing to apt.odio.love | The cross-repo dispatch. A personal access token scoped to `b0bbywan/odio-apt-repo`, so nothing else can trigger the rebuild from outside |
| `GPG_PRIVATE_KEY` | odio-apt-repo only | Signing the `Release` files, which `apt` verifies on every node before installing anything |
| `RELEASE_PAT` | odio-mympd, odio-qbz | Pushing the tag for a new upstream release, since a tag pushed with the default token starts no workflow |

PyPI needs no secret: the publishing job authenticates with a short-lived OIDC token bound to the repository and workflow, so there is nothing to store or rotate. Everything else (GitHub Releases, cross-repo asset downloads, Pages deploys) runs on the default `GITHUB_TOKEN`, scoped to each workflow run.

## Manual verification on hardware

On top of the automated matrix, two Raspberry Pis cover the manual checks:

- A **Pi 3B+** (arm64), a dedicated test rig, validates each PR: the [`pr-N` pre-release](#odios-releases) is run both as an upgrade from the previous release and as a reflash from the PR's image.
- A **Pi B+** (armv6), the maintainer's production node, takes every newly tagged stable as an upgrade from the previous one, after the release ships. A full playbook run takes around two hours there, so it stays off the mid-cycle loop.

Transcripts of these sessions, `PLAY RECAP` outputs with `failed=0`, and the upgrade paths walked are public in the [upgrade-system RFC](https://github.com/b0bbywan/odios/discussions/34), along with the hardware runs done while the upgrade system was being built.
